# تعليمات أسلوب الكود لـ Codex — مشروع FSOS (Field Sales OS)

هذه التعليمات لضبط أسلوب أي كود جديد أو معدّل في هذا المشروع بحيث يطابق الأسلوب المستخدم فعليًا في باقي الشاشات (مثال مرجعي: `apps/web/src/components/decision-analytics-studio/chart-engine.tsx`، `apps/web/src/components/charts/chart-color-scale.ts`). هذا الدليل معتمد كـ Code Style Contract لشاشة Smart Loading وأي عمل جديد لـ Codex داخل FSOS، ويُقرأ قبل أي تعديل في كود الفرونت إند.

## 1. تنسيق JSX/TSX

- كل عنصر JSX في سطره الخاص، بمسافة بادئة صحيحة (2 مسافة)، وليس كل الشجرة في سطر نصي واحد طويل.
- ممنوع كتابة كومبوننت كامل (return + JSX + منطق) في سطر واحد أو بضعة أسطر مضغوطة بفواصل منقوطة `;`. هذا يجعل المراجعة والتعديل شبه مستحيلين.
- الدوال المساعدة الصغيرة (`Metric`, `Field`, إلخ) تُكتب كل واحدة بجسمها الكامل مُنسّق، وليست مضغوطة في سطر واحد بعد الكومبوننت الرئيسي.

**خطأ (الأسلوب المستخدم في شاشة Smart Loading الحالية):**
```tsx
function Metric({label,value,strong}:{label:string;value:string;strong?:boolean}){return <div className="rounded-md bg-background/60 p-2"><p className="text-[11px] text-muted-foreground">{label}</p><p className={cn("mt-1 text-lg font-semibold",strong&&"text-teal-700")}>{value}</p></div>};
```

**صح (الأسلوب المتبع في باقي المشروع):**
```tsx
function Metric({ label, value, strong }: { label: string; value: string; strong?: boolean }) {
  return (
    <div className="rounded-md bg-background/60 p-2">
      <p className="text-[11px] text-muted-foreground">{label}</p>
      <p className={cn("mt-1 text-lg font-semibold", strong && "text-teal-700")}>{value}</p>
    </div>
  );
}
```

> **ملاحظة نطاق:** إعادة تنسيق شاشة Smart Loading الحالية (تحويلها من الأسلوب المضغوط لهذا الأسلوب) **لا تُعتبر تلقائيًا جزءًا من أي مهمة "إصلاح أخطاء" (bug fix)**. تُنفَّذ لاحقًا كمهمة Refactor منفصلة ومُعلنة صراحة، حتى لا تختلط إعادة التنسيق بمراجعة المنطق البرمجي في نفس التعديل.

## 2. الترميز (Encoding)

- كل ملف يُحفظ UTF-8 بدون BOM. لا تضِف `﻿` (BOM) في أول أي ملف.
- عند تعديل ملف موجود مسبقًا، لا تلمس الأحرف الخاصة الموجودة أصلاً (شرطات em-dash "—"، علامات اقتباس ذكية، إلخ) إلا إذا كان التعديل يستهدفها عمدًا. أي أداة أو سكربت تعالج الملف يجب أن تحافظ على الترميز الأصلي حرفيًا.
- بعد أي تعديل على ملف يحتوي نصوصًا عربية أو رموزًا خاصة، تحقق أن الملف ما زال يحتوي الأحرف الصحيحة. على ويندوز استخدم `rg` بدل `grep`:
  ```
  rg "â€|�" apps/web/src
  ```
  يجب ألا يعرض هذا الأمر أي نتائج مرتبطة بالملفات المعدَّلة في نفس المهمة.

## 3. الترجمة (i18n) — إلزامي لكل نص يظهر للمستخدم

- المشروع فيه نظام i18n مركزي في `apps/web/src/lib/i18n/dictionaries.ts` (مفاتيح مسطحة بنقطة فاصلة، نوع `TranslationKey`).
- أي نص عربي/إنجليزي يظهر في الواجهة يُضاف كمفتاح جديد في `dictionaries.ts` (القسمين AR وEN معًا)، ثم يُستخدم عبر `useTranslation()` من `@/components/translation-provider` — وليس نصًا عربيًا مكتوبًا مباشرة (hardcoded) داخل JSX.
- ممنوع إضافة مفاتيح لـ `dictionaries.ts` دون استخدامها فعليًا في الكومبوننت (مفاتيح ميتة). كل مفتاح جديد يُستخدم في نفس الـ commit الذي أضافه.

**خطأ (الأسلوب المستخدم حاليًا في smart-loading-screen.tsx):**
```tsx
<h1>التحميل الذكي</h1>
<p>تجهيز المركبة قبل بدء خط السير</p>
```

**صح:**
```tsx
const { t } = useTranslation();
// ...
<h1>{t("smartLoading.title")}</h1>
<p>{t("smartLoading.subtitle")}</p>
```

## 4. بيانات وهمية (Mock/Fixture)

- ممنوع وجود أي بيانات وهمية (fixture) يمكن أن تظهر للمستخدم النهائي تحت أي ظرف، حتى في بيئة `development`.
- إذا كانت هناك حاجة فعلية لبيانات معاينة أثناء التطوير المحلي، يجب أن تكون:
  - في ملف منفصل تمامًا خارج شجرة الكومبوننت الفعلي (وليس export من نفس ملف الشاشة الحقيقية)، أو
  - محكومة بمتغيّر بيئة صريح ومختلف عن `NODE_ENV` (مثل `NEXT_PUBLIC_USE_PREVIEW_DATA`)، بحيث لا يوجد احتمال أن يتفعّل تلقائيًا في أي بيئة تشغيل حقيقية.
- لا يجب أبدًا أن يُستبدل استعلام API الحقيقي (`useQuery`) بنتيجة ثابتة داخل نفس شرط الصفحة الأساسية.

## 5. التعليقات التوضيحية

- أي منطق عمل غير بديهي (معادلة حساب، عتبة رقمية، قرار تصميم) يُوثّق بتعليق مختصر فوقه يشرح "لماذا" وليس فقط "ماذا". راجع الأسلوب في `chart-color-scale.ts` و`smart-loading.service.ts` (الباك إند) كمرجع — التعليقات هناك مكتوبة جيدًا ويجب أن يُحافَظ عليها في الفرونت إند أيضًا.

## 6. حدود النطاق (Scope)

- أي مهمة محددة (مثل "بناء شاشة Smart Loading") لا تتضمن تعديل ملفات مشتركة حساسة إلا للضرورة المباشرة والمُعلنة (مثال: إضافة نوع جديد في `types.ts` نعم، لكن إعادة تهيئة الملف كله أو تغيير محتوى غير متعلق لا).
- أي تعديل خارج نطاق المهمة (خاصة في: `app.module.ts`، `main.ts`، أي ملف داخل `modules/assistant/`، `packages/schemas/index.ts`) يجب ذكره صراحة في تقرير التسليم مع سبب واضح، وليس تركه ليُكتشف لاحقًا عبر `git status`.

## 7. ترتيب مراجعة/تسليم أي مهمة على شاشة قائمة (مثال: Smart Loading)

عند مراجعة أو إصلاح شاشة موجودة، يجب اتباع هذا الترتيب بالضبط ولا يجوز تخطي خطوة أو دمجها:

1. إزالة سيطرة الـ Fixture على بيانات Development.
2. إصلاح ترميز الملفات المتأثرة (BOM وأي تلف mojibake).
3. استخدام مفاتيح i18n بدل النصوص hardcoded.
4. مراجعة المنطق والتصدير والتحديث (business logic, export, refresh).
5. تشغيل Typecheck.
6. مراجعة `git status` وفصل أي تعديلات خارج النطاق المُعلن.
7. بعدها فقط Commit وPush — وبعد إبلاغ المستخدم والحصول على موافقته الصريحة.

## 8. قبل تسليم أي مهمة

- شغّل `pnpm --filter @field-sales-os/web typecheck` (و`api` إذا كانت الشاشة تلمس الباك إند) وأرفق النتيجة كاملة في التقرير.
- تحقق من عدم وجود مفاتيح i18n غير مستخدمة، وعدم وجود fixture ظاهر، وعدم وجود تلف ترميز (باستخدام `rg` كما في القسم 2)، قبل الإعلان أن المهمة جاهزة للمراجعة.

## الرسالة القصيرة الثابتة لـ Codex

استخدم هذا النص كتعليمة ثابتة (system prompt أو أول رسالة) في أي مهمة تعديل فرونت إند داخل FSOS:

> قبل تنفيذ أي تعديل في FSOS، اقرأ واتبع `docs/codex-style-guide.md`. اكتب TSX منسقًا وواضحًا، استخدم i18n لكل نص ظاهر، احفظ UTF-8 بدون BOM، لا تعرض Fixture تلقائيًا، لا تعدّل ملفات خارج النطاق، وشغّل Typecheck قبل التسليم. أي خروج عن هذه القواعد يجب التصريح به قبل التنفيذ.
